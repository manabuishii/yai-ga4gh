# 言語と、他の言語でも実装しやすい設計(language)

- 作成: 2026-10-15。調べの元: `docs/research/2026-10-15_language-libraries.md`(版・日付・確認の方法はそちら)
- 書き方: **【確認済み】** = 公式のレジストリ・GitHub・実際に動かして確かめた(2026-10-15)/**【推定】** = 判断や見込み

## 1. 結論

**主の言語は Python のまま(FastAPI)。** 2026-10-15 22:3x のユーザーの指示(「結論が Python か Rust なら聞かずに進める」)に従い、そのまま進める(D-001 を確かめ直した)。

- 2 本目の言語は、**「4 つまとめた試験」と「相互運用の試験」が通ったあと**の「深める」段階で、1 つのサービスだけを別の言語で書く案として残す(候補は Go の TES か Rust の Clearinghouse の部品、【推定】)
- 理由は 3 節

## 2. 他の言語でも実装しやすい設計(言語に依らない部分を外に出す)

**共通にするのは 3 つだけ**(D-006、レビューで絞った)

| 何を | どこに | どう使う |
| --- | --- | --- |
| HTTP の契約 | `specs/` の OpenAPI(タグ固定、`spec-pins.md`)と、yai 独自の口(WES の stdout の口・DRS の配信口)・誤りの形 `{msg, status_code}` | 正。生成したモデル・形の検査はここから作る |
| 設定の意味 | `config/*.yaml`(信頼の表・利用者表・上限・許すホスト) | どの言語の実装も同じ設定で同じ振る舞い |
| 実装とは別に書いた期待する結果 | `tests/cases/*.yaml`(試験のデータ。表から作らず、手で書く) | 同じ試験が、別の言語の yai にも、相互運用の相手にも当たる |

**設計の正として持つが、実装の仕方は自由なもの**

| 何を | どこに | 実装の選択 |
| --- | --- | --- |
| 仕様の義務 | `docs/data/obligations.yaml` | 試験の名前の元 |
| 状態の移り方・認可・ページング | `docs/data/*.yaml` | 実行時に読む・コードに写す・型で表す(Rust の enum など)のどれでもよい。**どれでも同じ `tests/cases` に通ること**で確かめる |
| 保存の形 | 各実装の中(Python 版は SQLite) | 共有しない |

この形にすると、**別の言語で 2 本目を書いたときに「同じ試験で同じ答えになるか」を比べられる**。2 本の答えが食い違えば、どちらかの仕様の読み方が違う(4 節)。

## 3. Python と Rust・Go の比べ

| 観点 | Python | Rust | Go |
| --- | --- | --- | --- |
| OpenAPI からの生成(TES 1.1 で実際に動かした) | datamodel-code-generator 0.83.0・fastapi-code-generator 0.8.1 は成功。openapi-python-client 0.29.1 は失敗(応答コードの整数キーと外部 `$ref`)【確認済み】 | progenitor 0.15.1 は外部 `$ref` 未対応(issue #228 open)。openapi-generator の rust-axum は BETA【確認済み】。生成は試していない(手元に cargo が無い) | oapi-codegen v2.8.0 は成功(strict server あり)。ogen v1.24.0 は設定 1 行で成功【確認済み】。生成したコードのコンパイルは未確認 |
| DRS 1.5.0(分割・Markdown への `$ref`) | datamodel-code-generator は失敗(1 回だけ、原因未切り分け)【確認済み】 | 未試行 | 未試行 |
| JWT・JOSE | joserfc 1.7.5(既定で推奨のアルゴリズムだけ)、PyJWT 2.15.1(JWKS の取得とキャッシュ)。python-jose は 2025-05 から出ていない【確認済み】。`jku` の許可表は自分で書く | jsonwebtoken 11.1.0(JWKS の取得なし)。josekit・jose-jwk は更新が止まり気味【確認済み】 | lestrrat-go/jwx v3.3.0 は JWKS のキャッシュと `jku` の許可リストつき検証を持つ【確認済み】 |
| コンテナの操作 | docker 7.2.0(同期)【確認済み】 | bollard 0.21.1(非同期)【確認済み】 | `github.com/moby/moby/client` v0.6.2(置き場所が変わった)【確認済み】 |
| 既存の GA4GH 実装の言語(13 件) | 8(TESK・Sapporo・Toil・cwl-WES・drs-filer・indexd ほか)【確認済み】 | 1(stjude-rust-labs/tes)【確認済み】 | 2(Funnel・GBA-BI tes-api)【確認済み】 |
| 学習用の作りやすさ | 書く量が少なく、相互運用の相手のコードも Python が多くて読みやすい【推定】 | 書く量が最も多い。型で仕様を写す練習にはなる【推定】 | 中間。標準の HTTP と生成器がそろう【推定】 |

**Python 以外を主にしない理由**

1. 確かめた事実の中に、Python で困る点(生成器が無い・JWT のライブラリが無い・Docker を操作できない)が無い【確認済みの事実からの判断】
2. 相互運用の相手の多くが Python で、相手のコードを読む・直すのに同じ言語が有利【推定】
3. 「急ぎで 4 つ全部を動かす」に対して、書く量の少なさが効く【推定】
4. 型で防げる誤りの多くは、pydantic(入口の検査)+ pyright の strict + `assert_never`(状態の網羅)を CI で必須にすれば Python でも拾える【推定】

**気をつけること(Python で作るとき)**

- TES の OpenAPI は応答コードが引用符なしの `200:`(YAML では整数のキー)。形の検査・生成の道具に渡す前に文字列へ直す前処理を 1 か所に置く【確認済み】(`docs/spec-gaps.md` G-TES-11)
- 外部 `$ref`(service-info)は `specs/service-info/` へ置き換えてから道具に渡す(`spec-pins.md` 2 節)
- `jku` の許可表つきの鍵の取得は自分で書く(`aai.md` 3 節)。JWT の検証は joserfc か PyJWT で、アルゴリズムを必ず指定する

## 4. 別の言語でも実装する利点

| 種類 | 例 | 型で防げるか | 2 本目の言語で見つかるか |
| --- | --- | --- | --- |
| 状態の取り違え | 終わった TES タスクを RUNNING に戻す | 一部防げる(Rust の型状態なら「終わった状態から動かす関数」を書けなくできる)。enum と網羅の match・`assert_never` は**状態の値の取り違えは防ぐが、移り方が正しいかは保証しない**。移り方は表と試験で確かめる | 見つかる(片方だけ移り方を許す) |
| トークンの種類の取り違え | Passport を Bearer として受ける、PSAT を受ける | 防げる(種類ごとに別の型、Rust・Go)。Python は種類ごとに別の pydantic の型+pyright | 見つかる |
| 必須の欠け | `checksums` が空の DrsObject | 防げる(生成した型と検査) | 見つかりにくい(両方とも同じ生成器なら同じ) |
| 任意の項目の扱い | `next_page_token` の無い・空・null | 一部(Option は区別できるが、「空文字を終わり」と読むのは型ではない) | 見つかる |
| **仕様の読み違い** | `tokens[]` と `passports` の食い違いの解釈、`COMPLETE` に出力のアップロードを含めるか、Visa の期限の Option B | **防げない**(どちらも型としては正しい) | **見つかるのは、2 本を別々に読んで書いたときだけ**。同じ人が同じ解釈で書けば同じ誤りになる |
| 時刻・期限の意味 | `created_time` は中身の時刻か登録の時刻か、時計のずれ | 防げない | 同上 |

- まとめ: 2 本目の言語の利点は**型で防げる誤り**のほうが大きい。**解釈の誤り**は、型でも 2 本目でも防げず、`spec-obligations.md` の試験と、**他の人が書いた実装との相互運用の試験**のほうが見つけやすい【推定】
- だから 2 本目を書くより先に、相互運用の試験を置く(計画 第 3 版の順番)
