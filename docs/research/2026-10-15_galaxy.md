## 6. yai の設計に役立つ点と、仕様との違い

### 参考になる点
- DRS と WES で service-info を 1 つの関数から作る形(ga4gh.py)。yai でも共通化しやすい。確認済み
- DRS 用 ID を通常の API ID と別の鍵派生(`kind="drs"`)で符号化し、`hda-`/`ldda-` の接頭辞で種類を分ける。推測されにくい不透明 ID の作り方の例。確認済み
- チェックサム未計算なら 202 + Retry-After で非同期に計算させる。DRS 仕様の 202 の使い方の実例。確認済み
- GA4GH のパスだけエラー本文を仕様の形に変える例外ハンドラー(パスで分岐)。確認済み
- WES の run と task のページングを keyset トークンで実装。task id を「ステップ番号.ジョブ番号」にする設計。確認済み
- WES の出力に DRS URI を付け、WES→DRS をつなぐ形。yai の WES と DRS の連携試験の参考。確認済み
- DRS クライアントの compact identifier 解決(identifiers.org、キャッシュ、特例)。確認済み

### 相互運用の試験で問題になりそうな点
1. **DRS self_uri のホスト名に `drs.` が付く**: Galaxy が `localhost:8080` なら self_uri は `drs://drs.localhost:8080/hda-...`。yai がこの URI をそのまま解決すると到達できない。確認済み(datasets.py:560、wes.py:1106)
2. **DRS は公開データセットだけ・認証なし**: Passport/Bearer の試験相手にはならない。yai の AAI/Passport 1.2 との突き合わせは Galaxy では不可。確認済み
3. **POST /objects/{id} は Passport を読まない**、OPTIONS・bulk・/access は無し(access は常に 404)。確認済み
4. **チェックサムの type が大文字(`SHA-256`、`MD5`)**: yai 側で大文字小文字を区別すると不一致。enum は確認済み、出力値は推定
5. **チェックサムが無いと 202**: Celery を有効にしていないと計算されず、202 が続く可能性。推定(Celery 無効時の `.delay` の挙動は未確認)
6. DRS オブジェクトに `name` が無い(仕様上は任意)。確認済み
7. Galaxy クライアント → yai DRS: GET のみ・固定ヘッダーのみ。yai が Passport 必須にすると Galaxy からは取れない。`drs://localhost:8000/...` 形式はまず identifiers.org 問い合わせが走る。202 の再試行で認証ヘッダーが落ちる。https 既定(http は `force_http`)。確認済み
8. **WES の workflow_type が Galaxy 独自**(`gx_workflow_ga`/`gx_workflow_format2`)。yai が CWL/WDL を前提にすると噛み合わない。yai の WES クライアントから Galaxy を叩く試験なら、gxformat2 の YAML を添付すればよい。確認済み
9. WES の版表示は 1.0.0 だが、tasks エンドポイントなど 1.1 の機能がある。yai の WES 1.1 クライアントは `supported_wes_versions` だけで判断しないほうがよい。確認済み
10. **COMPLETE でもジョブがエラーのことがある**(Galaxy の completed の意味)。確認済み
11. `workflow_attachment` が 1 ファイルのみ・相対パス指定の扱いなし。確認済み
12. WES のエラー本文が `{err_msg, err_code}`。確認済み
13. `task_logs_url`・stdout/stderr が相対パス(仕様は URL)。確認済み
14. `system_state_counts` が常に 0、`auth_instructions_url` が "TODO"。確認済み
15. 認証は Galaxy の API キー(`x-api-key`)。Bearer は Galaxy の OIDC 連携を設定したときだけ。確認済み

## 7. 手元で docker で立てて試験する手間(すべて推定)
